Operating Room Module

UI/UX Guidance, Workflow Definition, and Implementation Requirements for the Hospital Operating Room (OR) Module.

Document Implementation Guide
Status Review Draft
Module Operating Room
Important: This document is an implementation and design guide, not an approved clinical protocol. Clinical workflows, required fields, permissions, and decision rules must be validated by the hospital before production use.

1. Overview

The Operating Room Module manages the documentation and workflow associated with preparing a patient for surgery, recording intraoperative activities, and documenting recovery and postoperative management.

The workflow begins when an authorized doctor selects Prepare for Surgery. The doctor records the surgery type and booking details. The system then initiates the surgery workflow and flags the surgery for Finance in the Payment Module.

The module should use existing HMS patient records, encounters, staff directories, consent handling, medication workflows, investigations, billing, and admission/transfer functionality wherever these capabilities already exist.

Primary Objective

Provide a clear, traceable workflow for surgical booking, preparation, intraoperative documentation, recovery, and postoperative care.

Design Principle

Keep the interface practical and easy to navigate. Reuse existing HMS functions rather than duplicating entire modules.

2. Scope and Design Principles

2.1 Included screens

  1. Surgical Booking / Prepare for Surgery
  2. Pre-operative Evaluation and Checklist
  3. Pre-operative Orders
  4. Intraoperative Record
  5. Operation Note
  6. PACU Recovery
  7. Post-operative Management

2.2 General UI/UX requirements

  • Display the patient and active encounter context on patient-specific screens.
  • Use consistent navigation, form controls, spacing, headings, and status indicators.
  • Keep related fields grouped into clearly labeled sections.
  • Show readable labels and units where applicable.
  • Provide clear validation messages and save confirmation based on the actual result.
  • Preserve entered information when a recoverable error occurs, where technically possible.
  • Support smaller screens without hiding essential actions.
  • Use the existing HMS authentication and authorization patterns.

3. End-to-End Workflow

The proposed OR workflow consists of initiation and identification, finance pricing, pre-operative preparation, intraoperative documentation, and postoperative recovery.

1

Initiation and Identification

An authorized doctor selects or enters the surgery type, records booking details, and uses Prepare for Surgery to initiate the workflow.

2

Finance Pricing

The system flags the surgery in Payment Module → Surgery Payment. Finance selects the applicable pricing option.

3

Pre-operative Preparation

The team documents surgical assessment, anesthesia evaluation, checklist items, consent, and pre-operative orders.

4

Intraoperative Documentation

The team records the surgical record, anesthesia record, circulating nurse notes, instrument and sponge counts, and operation note.

5

Postoperative Recovery

The team records PACU observations, pain score, consciousness level, Aldrete score, postoperative orders, and progress notes.

This is the proposed system workflow. It does not replace hospital-approved clinical checklists or authorize automatic clinical decisions.

4. Screen 1 — Surgical Booking / Prepare for Surgery

4.1 Purpose

Create or open the surgery record using the existing patient and encounter context. Capture the required booking details and initiate the downstream workflow.

4.2 Required fields and actions

Field / Action Expected Behavior
Prepare for Surgery Initiates the configured surgery workflow using the existing patient/encounter context.
Surgery Type Doctor selects an existing value or types a new surgery name.
Preoperative Diagnosis Records the preoperative diagnosis.
Planned Procedure Records the planned procedure.
Surgeon Uses the existing staff directory where available.
Assistant Surgeon Uses the existing staff directory where available.
Anesthetist Uses the existing staff directory where available.

4.3 Surgery Type behavior

The supplied requirement describes Surgery Type as a self-learning list. The interface should support selecting an existing value or typing a new name.

The precise behavior for storing new names, matching similar names, preventing duplicates, and reviewing new entries must be confirmed before implementation.

4.4 Expected result

  • A surgery record is created or opened.
  • The patient and encounter association is retained.
  • The surgery becomes available to the configured workflow.
  • A finance task is flagged after the surgery type is entered.

5. Finance Handoff and Surgery Payment

5.1 Responsibility separation

Clinical staff enter surgery information. Finance handles pricing in the Payment Module. The OR interface should not expose surgery price or package editing to clinical staff unless the hospital explicitly approves a different permission model.

5.2 Finance workflow

  1. The doctor enters the surgery type.
  2. The system flags the item in Payment Module → Surgery Payment.
  3. Finance reviews the surgery payment task.
  4. Finance selects the applicable pricing option.
  5. The payment decision is recorded in the existing billing workflow.

5.3 Pricing options

Option Meaning Responsible Role
Direct Surgery Price Applies the price for the surgery procedure only. Finance
Offer Package Applies a package that may include surgery service, medication/pharmacy, consumables, and other treatments. Finance
The exact billing rules, package definitions, price calculations, payment status requirements, and any surgery scheduling restrictions must come from the existing HMS billing design and hospital policy.

6. Screen 2 — Pre-operative Evaluation and Checklist

6.1 Surgical Assessment

Required Field Purpose
Diagnosis Documents the surgical diagnosis.
Procedure Planned Documents the planned operation.

6.2 Anesthesia Evaluation

Required Field UI Requirement
ASA Classification Capture the classification selected by the authorized clinician.
Airway Assessment Provide a field for the documented assessment.
Allergies Display or capture allergy information according to the existing HMS allergy workflow.

6.3 Pre-operative Checklist

  • Consent Signed
  • Blood Available
  • Site Marked
  • Investigations Reviewed
  • Fasting Status Checked
  • Jewelry Removal Checked

The first four fields are the explicitly supplied checklist requirements. Fasting status and jewelry removal are also included in the supplied workflow description.

6.4 Consent Management

The system should support the hospital-approved method for recording consent, including digital consent or uploading the relevant consent document.

Consent document access, signing, version history, and retention should follow the existing HMS document and audit approach.

7. Screen 3 — Pre-operative Orders

Provide a clear form for documenting the authorized pre-operative orders. Medication orders should reuse the existing medication and pharmacy workflow where available.

Required Field Expected UI Behavior
NPO Status Record the authorized NPO instruction.
IV Fluids Document the authorized fluid order.
Antibiotic Prophylaxis Record the authorized order through the applicable medication workflow.
Blood Products Document the authorized order.
DVT Prophylaxis Document the authorized order.
Do not invent medication doses, fasting intervals, antibiotic regimens, blood product rules, or DVT protocols. These must follow approved hospital policies and authorized clinical orders.

8. Screen 4 — Intraoperative Record

8.1 Surgical Record

  • Procedure Performed
  • Operative Findings
  • Estimated Blood Loss
  • Complications

8.2 Anesthesia Record

  • Drugs Administered
  • Monitoring Record
  • Fluid Balance

8.3 Circulating Nurse Note

Provide a dedicated area for the circulating nurse to record relevant notes and observations. Timestamping and recorder identity should follow the existing HMS audit pattern.

8.4 Instrument and Sponge Count

Required workflow checkpoint: The supplied requirements specify instrument and sponge count documentation before incision closure.

The system should provide a clearly visible place to record the count status and related documentation. The exact count procedure, discrepancy handling, escalation, and authorization requirements must follow hospital-approved policy.

The application must not silently treat a missing count as completed. Any blocking or escalation behavior must be confirmed with the hospital before development.

9. Screen 5 — Operation Note

The operation note provides a consolidated record of the procedure and its key findings.

Required Field Notes
Preoperative Diagnosis Diagnosis before the operation.
Postoperative Diagnosis Diagnosis after the operation.
Procedure Performed Actual procedure performed.
Findings Operative findings.
Specimens Sent Document specimens sent, where applicable.
Complications Document complications or status.
Estimated Blood Loss Record the estimate and appropriate unit.
Surgeon Record the responsible surgeon.
Assistant Record the assistant.
Anesthetist Record the anesthetist.

9.1 Documentation behavior

  • Associate the note with the correct surgery record.
  • Record the author and relevant timestamps.
  • Use existing HMS draft, signature, and finalization patterns.
  • Preserve audit history for approved corrections.

The precise signature, locking, and amendment rules remain subject to confirmation with the hospital and the existing HMS implementation.

10. Screen 6 — PACU Recovery

The PACU screen captures recovery observations after the operation and anesthesia.

Required Field Documentation Requirement
Vital Signs Record observations using approved fields and units.
Pain Score Capture the score and applicable scale.
Consciousness Level Record the documented assessment.
Aldrete Score Capture the score according to the approved process.

10.1 UI/UX guidance

  • Keep patient and surgery context visible.
  • Provide clearly labeled fields for recovery observations.
  • Display recorded values and timestamps clearly.
  • Reuse existing observation and clinical documentation patterns.
Aldrete scoring rules, recovery monitoring frequency, discharge criteria, and clinical thresholds must not be invented by the frontend developer. Use the approved hospital process.

11. Screen 7 — Post-operative Management

Provide a structured area for documenting postoperative management and progress.

Required Field Expected Behavior
Analgesics Record or reference the authorized medication order.
Antibiotics Record or reference the authorized medication order.
IV Fluids Document the authorized fluid order.
Diet Document the authorized diet instruction.
Mobilization Document the authorized mobilization instruction.
Postoperative Progress Notes Capture clinical progress documentation.

11.1 Existing HMS integration

Medication administration, pharmacy, ward transfer, ICU transfer, and other destination handoffs should use existing HMS workflows where available.

The OR module should not independently create duplicate medication, billing, admission, or transfer systems when the required functionality already exists.

12. Roles and Permissions

The following is a proposed responsibility separation based on the supplied workflow. Final access permissions must match the existing HMS authorization model and hospital policy.

Role Proposed Responsibility
Doctor / Surgeon Surgery booking, diagnosis, planned procedure, clinical assessment, and applicable notes/orders.
Anesthetist Anesthesia evaluation, anesthesia records, and applicable clinical documentation.
Operating Room Nurse Applicable nursing records, checklist documentation, and count records according to assigned responsibilities.
PACU Staff Recovery observations and related documentation according to assigned duties.
Finance Surgery pricing and package selection in the Payment Module.
System Administrator Technical configuration and access administration according to existing policy.
These role descriptions are a starting point, not a finalized permissions matrix. Do not grant or remove access without comparing against the existing HMS roles.

13. Integration with the Existing HMS

The OR module should extend the existing HMS rather than duplicate its core functionality.

Existing HMS Capability Expected Integration
Patient Records Reuse existing patient identity and record.
Encounter / Admission Associate surgery with the appropriate encounter.
Staff Directory Reuse available staff selection and identity.
Payment / Billing Flag the surgery in Payment Module → Surgery Payment for Finance.
Medication / Pharmacy Reuse the established medication and pharmacy workflows.
Investigations Reuse available investigation records and results.
Consent / Documents Reuse the approved document storage and consent workflow.
Admission / Transfer Use existing ward, ICU, and transfer functionality where available.
Audit Follow existing record history and correction patterns.

13.1 Implementation approach

  1. Inspect the current HMS navigation and patient context.
  2. Identify existing routes, components, services, and APIs.
  3. Map each OR requirement to an existing capability where possible.
  4. Identify genuine gaps before creating new components or endpoints.
  5. Implement only approved additions.
  6. Test existing ICU and other HMS functions for regressions.

14. Safety, Validation, and Audit

14.1 Patient and encounter context

Patient-specific records must be associated with the correct patient and active encounter. The interface should make this context visible to authorized users.

14.2 Clinical documentation

  • Do not silently overwrite finalized clinical records.
  • Use the approved correction and audit process.
  • Record staff identity and timestamps according to existing rules.
  • Display clear validation and save-result messages.
  • Do not report successful saving before the server confirms it.

14.3 Clinical rules requiring approval

  • Mandatory field rules and which roles can complete them.
  • Instrument and sponge count discrepancy handling.
  • Consent requirements and verification behavior.
  • Medication order and verification rules.
  • ASA classification handling and anesthesia documentation.
  • PACU monitoring and Aldrete scoring behavior.
  • Recovery, discharge, and transfer criteria.
The prototype interface alone is not suitable for real clinical use. Production deployment requires server-side validation, access control, persistence, auditability, and clinical review.

15. Implementation and Acceptance Checklist

Use this checklist during implementation review. Mark an item complete only after the behavior has been implemented and tested in the actual HMS environment.

15.1 Booking and finance

  • Correct patient and encounter context is displayed.
  • Surgery Type supports selection and typed input.
  • Booking fields are available.
  • Prepare for Surgery triggers the approved workflow.
  • Finance task appears in the correct payment location.
  • Pricing options are controlled by Finance permissions.

15.2 Pre-operative workflow

  • Surgical Assessment fields are available.
  • Anesthesia Evaluation fields are available.
  • Pre-operative checklist is available.
  • Consent handling follows the approved workflow.
  • Pre-operative Orders fields are available.

15.3 Intraoperative workflow

  • Surgical Record fields are available.
  • Anesthesia Record fields are available.
  • Circulating Nurse Note is available.
  • Instrument and sponge count documentation is available.
  • Count checkpoint behavior is validated against policy.
  • Operation Note fields are available.

15.4 Postoperative workflow

  • PACU Vital Signs field is available.
  • Pain Score field is available.
  • Consciousness Level field is available.
  • Aldrete Score field is available.
  • Post-operative management fields are available.
  • Existing transfer and medication workflows are reused.

15.5 Technical acceptance

  • Role permissions are enforced on the server.
  • Records persist correctly in the database.
  • Audit history is preserved.
  • Error and success states are tested.
  • Responsive layout is tested.
  • Existing HMS and ICU functions continue to work.

16. Open Questions Before Production

These points need confirmation before the implementation becomes a production clinical workflow.

Question Why It Matters
How should new Surgery Type names be stored and reviewed? Avoid duplicate names and unintended self-learning behavior.
What conditions, if any, must be met before surgery scheduling? The system must follow approved hospital workflow rather than inventing restrictions.
What is the exact instrument and sponge count discrepancy process? The workflow must match approved clinical policy and responsibilities.
Which fields require signatures or countersignatures? Determines authorization, finalization, and amendment behavior.
What are the approved PACU scoring and recovery procedures? Prevents the application from inventing clinical rules.
Which existing HMS APIs and components support the workflow? Ensures correct integration and avoids duplicate systems.
What billing statuses and pricing rules already exist? Keeps the finance handoff consistent with existing billing behavior.
Implementation principle: Build the OR module around the hospital's actual workflow, preserve the supplied field requirements, reuse existing HMS capabilities, and obtain approval for unresolved clinical and operational rules before production deployment.
